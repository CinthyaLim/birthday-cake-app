Reading the Cake

A guided tour of a Jetpack Compose game, written for the person who owns it — the architecture, the decisions, and the bugs each one prevents.

Three screens, one cat, a memory-matching mini-game and a mixing bowl. Underneath: two ViewModels, a dialogue system made entirely of data, and a set of deliberate choices worth being able to defend.

01

The big picture

A birthday card you play instead of read. A cat wakes up, shows you a recipe, discovers the pantry is empty, sends you off to find the ingredients in a memory game, then lets you drag what you found into a bowl. Mix, and you get a cake.

No network, no database, no login. Everything lives in memory and the whole thing lasts about two minutes. That's worth saying out loud in a README: this app has no persistence layer because it doesn't need one. A reviewer who sees no Room database will either assume you didn't know how, or that you made a call. Make it clear you made a call.

The mixing screen is visited twice. First with an empty pantry, then stocked. Same composable both times — there is no "empty pantry screen" and "stocked pantry screen", there is one screen that draws whatever state it is given.

The idea that repeats

One component, many states. It shows up in every corner of this codebase — the dialog panel that renders a one-liner or a twelve-row recipe card, the chip that's live or dimmed, the page that's empty or full. Hold onto it.

Self-check · 01
The mixing page appears twice. What differs, and where does that difference live?
The chips are stocked instead of empty, and the difference lives entirely in GameUiState.inventory — the composable is byte-for-byte identical both times. First visit: GameData.emptyInventory. Second: whatever onHuntFinished banked.
Trace the chain from "board cleared" to "FINAL screen showing".
MiniHuntPage → onFinished → GameViewModel.onHuntFinished sets inventory and shows HUNT_WON → player taps through → onSequenceComplete(HUNT_WON) → goTo(MIXING) → player drags and taps Mix → onMixClick → goTo(FINAL). Note the mini-game does not go to FINAL — going straight there would skip the bowl.
Why is DialogCatalog in data/ and not ui/?
Because it's a script, and scripts aren't UI. It holds string resource ids, not resolved strings, so it needs no Context and no composable scope. You can test it, print it and translate it without Compose ever entering the picture.
To add a fourth screen, which files must you touch?
GameScreen.kt, the when in MainActivity (the compiler forces this — it's exhaustive), a new file in ui/screen/, and onSequenceComplete if a dialog leads into it. The compiler catches two of the four for you.
02

State in Compose

This is the section that matters most. Everything else in the project is an application of what's here.

Recomposition, honestly

A @Composable is not a normal function. Compose calls it again whenever something it read has changed. mutableStateOf creates an observable box; remember stops that box being rebuilt on every pass; reading it subscribes the enclosing scope.

The correction most people need: recomposition is not a redraw and it is not cheap by magic. It's a re-execution of your Kotlin. Anything you allocate inline is allocated again — so a lambda, an object : ..., or a list built with map is a new object every recomposition. When a Compose API compares old and new to decide whether something changed, new-every-time means "always changed". That single fact shaped the dialog system and the drag-and-drop target.

Where state can live

HomeSurvives rotationUsed here for
remember { mutableStateOf() }NoisOver — is a finger hovering the bowl. Losing it on rotation is fine.
rememberSaveableYesNot used — nothing local here is worth saving.
ViewModelYesBoth games' real state. Rotate and your cards stay flipped.

The project's own justification is worth reading, because it isn't "best practice":

From GameViewModel's doc comment

State lives in a view model rather than in a remember because finishing a conversation changes the game: the pantry dialog ends and the hunt begins. Screen and dialog have to move in one update or the scrim flickers between them, and a composable holding one half of that cannot promise it.

That's a correctness argument — two facts must change atomically. If screen lived in one remember and dialog in another, there'd be a frame where one had changed and the other hadn't. That's how architecture should be justified: not "the docs say so", but "here's the bug it prevents".

The StateFlow pipeline

// 1. private mutable holder
private val _uiState = MutableStateFlow(GameUiState())

// 2. public read-only view of the same holder
val uiState: StateFlow<GameUiState> = _uiState.asStateFlow()

// 3. the composable subscribes
val game by gameViewModel.uiState.collectAsStateWithLifecycle()
  • asStateFlow() returns a read-only wrapper. Without it a composable could write uiState.value = ... and the whole unidirectional discipline evaporates.
  • collectAsStateWithLifecycle() stops collecting below STARTED. Plain collectAsState() keeps working while backgrounded.
  • by is property delegation — it needs the getValue import, and forgetting it is a confusing compile error.

Why every write goes through update

fun onIngredientDropped(id: String) {
    _uiState.update { state ->
        val held = state.pantry.firstOrNull { it.ingredients.id == id }
        if (held == null || held.currentAmount <= 0) return@update state  // guard
        state.copy(bowl = state.bowl + (id to (state.bowl[id] ?: 0) + 1))   // write
    }
}

The check "do we still have one of these?" and the write "put one in the bowl" sit inside the same lambda. Pull the check outside and two fast drops could both pass it and both write — eleven ingredients in a ten-ingredient bowl. update is a read-modify-write that retries on conflict; .value = .value.copy(...) is three separate steps.

Stored vs derived state

The one idea to take away

Every stored field is a promise you must keep on every update path. Every derived field is a promise the compiler keeps for you. MiniHuntUiState stores two fields and derives seven.

data class MiniHuntUiState(
    val cards: List<MemoryCard> = emptyList(),   // STORED
    val moves: Int = 0                            // STORED
) {
    val revealed get() = cards.filter { it.isFaceUp && !it.isMatched }
    val isMismatched get() = revealed.size >= 2
    val matchedPairs get() = cards.count { it.isMatched } / 2
    val isFinished get() = cards.isNotEmpty() && matchedPairs == totalPairs
    // ...three more, all derived
}

The sharpest case is isMismatched. Stored, you'd set it true on a miss and a coroutine would clear it a second later. If that coroutine is cancelled — a restart, a rotation, anything — the flag is stuck on and the board is dead. Derived from the cards, that bug cannot be written.

The same rule runs through GameUiState (five stored, seven derived) and ActiveDialog, which stores where you are and derives what to show:

data class ActiveDialog(val sequence: DialogSequence, val index: Int = 0) {
    val step get() = sequence.steps[index]
    val isLast get() = index == sequence.steps.lastIndex
}

And the pantry, which is neither of the two things it's made of:

val pantry get() = inventory.map {
    it.copy(currentAmount = it.currentAmount - (bowl[it.ingredients.id] ?: 0))
}

Which is why dragging into the bowl never touches the inventory. One write to bowl, two visible effects, zero chance of them disagreeing.

@Immutable, and the danger in it

@Immutable is a promise to the compiler: these properties will never change, so an unchanged reference means unchanged content. Given that, Compose can skip recomposing. It matters most for List<T>, an interface that could be backed by something mutable.

If you lie, you get stale UI with no error. No crash, no warning, no log — the screen just stops updating. It is the most dangerous annotation in Compose, because it disables a safety check in exchange for speed. Which is why every update here is a copy() and never an in-place mutation.

Hoisting, and the stateful/stateless pair

MixingPage takes pantry, bowlCount, isMixReady in and sends onIngredientDropped, onMixClick out. It's a pure function of its parameters — which is why the file ends with three previews showing empty, stocked and ready-to-mix states.

MiniHuntPage looks like an exception, taking a ViewModel — but it immediately delegates to a private overload that takes plain state. The public one wires; the private one draws. That's what makes its five previews of specific board states possible. The rule worth copying: only one composable per screen should know a ViewModel exists.

Self-check · 02
Why store moves but derive matchedPairs? Both are counters.
moves is not derivable — nothing on the board records how many attempts were made, since a matched pair looks identical whether found on try 1 or try 30. It's an irreducible fact. matchedPairs is derivable, so it isn't stored. The test is always: can I compute this from what I already store?
What breaks if pantry became a stored field?
Two things. You'd have to remember to update it on every path touching inventory or bowl — miss one and the chips lie. And inventory and pantry would both claim to be the truth, with no way to tell which is right when they disagree.
You add @Immutable to a class holding a MutableList you mutate in place. What happens, and when do you notice?
Compose sees the same reference, believes the promise, skips recomposition, and the new items never appear. No crash, no warning, no log. You notice when a user reports the screen "not updating", and you lose an afternoon.
Why does MiniHuntPage have two overloads with the same name?
The stateful/stateless split. The public one takes a ViewModel, collects its state and runs the LaunchedEffects; the private one takes plain MiniHuntUiState and only draws. That split is what makes rendering a mid-game board in a preview possible without constructing a ViewModel.
03

The game flow

GameViewModel is 136 lines including comments, and its whole public surface is one StateFlow and five methods: onDialogAdvance, onHuntFinished, onIngredientDropped, onMixClick, onPageExpression.

Five events. That's every input the game can receive; everything else is a consequence computed from them. When you can list every way state changes on one hand, you can reason about all of them.

The checkpoint table

private fun onSequenceComplete(id: DialogSequenceId) = when (id) {
    DialogSequenceId.INTRO    -> show(DialogSequenceId.RECIPE)
    DialogSequenceId.RECIPE   -> show(DialogSequenceId.RAN_OUT)
    DialogSequenceId.RAN_OUT  -> goTo(GameScreen.HUNT_INGREDIENTS)
    DialogSequenceId.HUNT_WON -> goTo(GameScreen.MIXING)
    DialogSequenceId.FINALE   -> Unit   // terminal
}

The entire plot of the game is these five lines. Read top to bottom and you have the story. Three properties earn their keep:

  • It's exhaustive. Used as an expression over an enum, so adding a sixth sequence stops the file compiling until you say what happens when it ends. The compiler makes you finish the thought.
  • It's the only place consequences live. No dialog step carries an onFinish lambda. One place to look.
  • FINALE -> Unit is doing real work. It's the explicit statement that the game ends here — deleting the branch wouldn't compile.

The ordering that prevents a soft-lock

fun onDialogAdvance() {
    val current = _uiState.value.dialog ?: return
    val next = current.next()

    if (next != null) {
        _uiState.update { it.copy(dialog = next) }
    } else {
        _uiState.update { it.copy(dialog = null) }   // clear FIRST
        onSequenceComplete(current.sequence.id)      // then act
    }
}

Because onSequenceComplete may call show(...), which sets a new dialog. Run it before the clear and you'd erase the dialog you just opened — the game freezes with nothing showing and no way to continue. One line of ordering separates a working game from a soft-lock.

Screens without a navigation library

A when over an enum in MainActivity. No NavHost, no routes, no back stack. Defensible, and you should be able to defend it: three screens, strictly linear, no deep links, no arguments to serialize, and back is actively blocked during dialogs.

It stops being right the moment you want a back stack, a settings screen you can return from, or transitions between screens. Knowing where that line is is more impressive than having picked a library.

Two sources for one cat face

val expression: CharacterExpressions
    get() = dialog?.step?.expression ?: pageExpression

A dialog always wins — if someone's talking, they own the face. Otherwise the page decides. One line, no flags, no priority system. The mini-game never draws a cat; it reports a mood and something else draws it.

The one delay in the game

fun onMixClick() {
    if (!_uiState.value.isMixReady) return

    goTo(GameScreen.FINAL)
    viewModelScope.launch {
        delay(FINAL_PAGE_BEAT_MS)      // 900ms
        show(DialogSequenceId.FINALE)
    }
}

Without it, the cake, confetti, title and a dimming scrim all arrive in the same frame — you'd never see the cake, the thing the whole game was building toward. Show the page, let it land, then talk.

Note the guard on the first line. The button is already disabled when the bowl isn't full, so this looks redundant — it isn't. The disabled button is a UI affordance; this is the rule. Never let a disabled button be the only thing enforcing a rule.

Self-check · 03
Add a THANK_YOU sequence after FINALE. What breaks, and is that good?
Compilation, in exactly two places: sequenceFor (what does it say?) and onSequenceComplete (what happens when it ends?). That's good — those are precisely the two decisions you must make. A Map lookup would compile fine and crash at runtime.
Why HUNT_WON → goTo(MIXING) and not FINAL?
Because the bowl still has to be filled. The hunt gives you ingredients; it doesn't bake. Going straight to FINAL would skip the drag-and-drop half of the game entirely.
onIngredientDropped("pickles") — trace it.
firstOrNull returns null, the guard hits, return@update state returns the state unchanged. Nothing happens, nothing crashes — and there's a test for it. Since the id arrives from a drag-and-drop ClipData, a string from outside your type system, validating it isn't paranoia.
The 900ms delay could have lived in FinalPage. Why doesn't it?
Because the page's job is to draw a cake, not to sequence the story. Sequencing is the ViewModel's job — the same principle that keeps consequences in the checkpoint table. Practically: viewModelScope cancels the delay if the ViewModel dies, and the timing stays visible in the file you'd actually read to understand the flow.
04

Dialog as data

The most interesting design in the project. If someone asks you to walk through one part of this codebase, walk through this.

The obvious approach is a composable per conversation with its own step counter and its own idea of what a dialog looks like. It works, and then you have five of them, and changing the panel style means editing five files.

The approach taken: a dialog is a list of values. There is one renderer in the entire app; everything else is content fed into it.

val intro = DialogSequence(
    DialogSequenceId.INTRO,
    listOf(
        DialogStep(expression = SLEEPING, header = DialogText(R.string.intro_sleep)),
        DialogStep(expression = YAWNING,  header = DialogText(R.string.intro_ask)),
        DialogStep(
            expression = LAUGHING,
            header = DialogText(R.string.intro_today_header),
            desc   = DialogText(R.string.intro_today_desc),
            button = DialogButton(DialogText(R.string.intro_today_button))
        ),
    )
)

Adding a line is an edit to one list plus a string in strings.xml. Nothing in the overlay, the frame or the animation needs to know.

Copy that isn't a String

data class DialogText(@StringRes val resId: Int, val args: List<Int> = emptyList())

Resolving a resource needs a Context. If the catalog held resolved strings it would need one too — and then it couldn't be a plain object, and a JVM unit test couldn't read it. Keeping it an id means resolution happens at the last possible moment, inside the composable that draws it.

And List<Int> rather than List<Any> is deliberate: every argument in this game is a number, and restricting the type guarantees the whole thing is comparable by value. Which matters enormously, for the reason below.

The no-lambdas rule

The bug this design exists to prevent

Two lambdas are never equal, and a lambda written inline in a composable isn't even equal to itself from the previous frame. Put one on a data class and its generated equals() is permanently false.

Work through the chain. AnimatedContent decides "has the content changed?" by comparing old and new. DialogStep is a data class, so equals() covers every constructor property. Add onClick: () -> Unit and stepOld == stepNew is always false, even when nothing changed — so AnimatedContent restarts its transition on every recomposition and the dialog flickers continuously.

It's a miserable bug to diagnose, because the code looks right: the text is correct, the index is correct, nothing is null. The fix taken here is that steps carry no behaviour at all. Every button in the game calls onAdvance; what advancing means is the checkpoint table's business.

The general principle

Put behaviour where it's decided, not where it's displayed. Any data class feeding an equality-sensitive API — AnimatedContent, key(), derivedStateOf, skipping — must hold only comparable values.

Sealed, not nullable

sealed interface DialogExtra {
    data class Recipe(val entries: List<RecipeEntry>) : DialogExtra
    data class Pantry(val slots: List<IngredientsCount>, val columns: Int = 3) : DialogExtra
}

Two dialogs carry a structural block; they need different payloads, and a step can only ever have one. The nullable-fields alternative can't express "exactly one of these" — nothing would stop both being set, and pantryColumns would be meaningless without pantrySlots.

Sealed does express it, and it pays off at the render site: the when in DialogStepBody is exhaustive, so adding a variant walks the compiler to the exact line where the new branch belongs.

A small i18n grace note

Headers can contain [[TODAY]], which the renderer converts into an AnnotatedString with a pink highlight. The alternative — "highlight any ALL-CAPS word" — breaks the moment a translator uses a language without that convention. Putting the markup in the translatable string makes emphasis a translator's decision.

Self-check · 04
Explain the flicker to someone who knows Compose basics.
DialogStep is a data class, so equals() includes every property. Lambdas have identity equality and are recreated every recomposition, so oldStep == newStep would always be false. AnimatedContent reads that as a content change and restarts its fade every recomposition — a permanently flickering dialog whose cause isn't visible anywhere near the animation code.
Why is intro a val but huntWon(...) a fun?
intro is fixed copy — same six lines every time, so it's built once. huntWon embeds a live number into "You found %d things!", so it can't exist until that number does. Static content → val; content reading live state → fun.
Name two things that become impossible if DialogText held a String.
The catalog could no longer be a plain object — resolving needs a Context, so it'd need construction and injection. And the JVM unit tests couldn't run without Robolectric or an emulator. A third: localisation breaks, since the string would resolve once at class-init in whatever locale was active then.
Every button calls onAdvance. Doesn't that mean they all do the same thing?
At the UI level, yes — they advance. What advancing means depends on where you are, and that lives in onSequenceComplete. The trade: buttons lose per-step flexibility, and in exchange the whole plot is five readable lines. Right for a linear story; a branching dialogue tree would want an action: DialogAction enum on the step — still data, still comparable.
05

The dialog overlay

416 lines, the largest file in the project, and most of it is careful animation timing.

Why not a real Dialog

Compose has ui.window.Dialog. It isn't used, for two independent reasons. A platform dialog is a separate window, so its dim would fall over the whole app — cat included — and putting the character back on top would mean drawing a second one inside the dialog window. And a window boundary makes a shared size animation impossible, when the panel has to grow smoothly from a two-line greeting to a twelve-row recipe card.

So the overlay is a Box drawn on top, in the same composition. Z-order in a Compose Box is declaration order — page, overlay, cat — and that single ordering is the whole solution.

Holding the last value through the exit

var shown by remember { mutableStateOf(active) }
if (active != null && active != shown) shown = active

When a conversation ends, dialog becomes null immediately — but the fade needs 220ms. Draw from active and the panel empties instantly and you watch a blank box fade away. active controls whether it's visible; shown controls what's drawn.

Explicit identity

contentKey = { it.sequence.id to it.index }

Two scenarios the default == would get wrong. INTRO ends and RECIPE starts — both at index = 0, so an index-only key sees no change. And two adjacent steps with identical copy (the finale reuses one of the intro's strings) would compare equal and skip the transition. The pair distinguishes both, and is cheaper than deep-comparing a whole sequence.

Read target, never the captured state

One of the most common Compose animation bugs

The content lambda runs twice during a transition — once for the outgoing state, once for the incoming. target is the right one for that invocation. active is captured from the enclosing scope and always holds the newest value, so reading it makes the outgoing copy recompose with the new content. You'd be crossfading step 4 into step 4.

Three things happening at once

val enter = fadeIn(tween(CONTENT_IN_MS, delayMillis = CONTENT_OUT_MS)) +
    slideInVertically(...) { fullHeight -> fullHeight / 12 }

val exit = fadeOut(tween(CONTENT_OUT_MS))

enter togetherWith exit using SizeTransform(clip = true) { initialSize, targetSize ->
    val delta = abs(targetSize.height - initialSize.height)
    tween((SIZE_MIN_MS + delta * SIZE_MS_PER_PX).roundToInt().coerceIn(220, 420), ...)
}
  • The 90ms gap is the point. The incoming fade is delayed until the outgoing one has finished — two lines of body copy legible at once read as mud rather than as a change.
  • clip = true is required. Without it, a tall recipe card renders at full height while the cream frame is still growing, and text hangs outside the box.
  • Distance-scaled duration. A one-word change moves ~0px → 220ms; the jump to the recipe card moves ~400px → 360ms. Physical motion takes longer over longer distances, and matching that is why it feels right. Every future variant inherits it free, because SizeTransform interpolates an IntSize and doesn't care what's inside.

Blocking input, twice

Back is handled by BackHandler(enabled = active != null) { }. The empty body is the point: registering a handler intercepts the press, and doing nothing with it consumes the event. Scoped by enabled, so back works normally on the memory board.

Touches are eaten by a modifier that consumes every pointer event on the scrim. And yet tapping the panel still advances the dialog — because pointerInput defaults to PointerEventPass.Main, which is delivered topmost node first. The panel is a later sibling, so it's above the scrim and gets first refusal; only what misses the panel reaches the scrim, where it dies. Switch to Initial and the dialog becomes unadvanceable.

A preview that checks a decision

The file's last preview renders the overlay over a real page inside the real scaffold. Component previews check a component; this one checks that the layering is right and there's exactly one cat on screen. Worth the habit: preview the composition, not just the components.

Self-check · 05
Why does shown exist when active is right there?
For the exit animation. active goes null the instant a conversation ends, but the fade-out needs 220ms. shown holds the last non-null value so there's still content to draw on the way out.
The scrim consumes all pointer events, yet the panel still works. Explain.
Pointer events are delivered in passes, and pointerInput defaults to Main, which goes topmost-node-first. The panel is declared after the scrim so it's above it in z-order and receives the event first. Only touches that miss the panel reach the scrim to be consumed.
Why is the size duration computed from the height delta rather than fixed?
Because a fixed duration is wrong at one end or the other — a one-word change over 400ms feels sluggish, a 400px jump over 220ms feels abrupt. The formula gives short hops a snappy floor and long ones proportionally more time, with a ceiling so a huge jump never drags.
06

The memory game

The hunt must produce exactly the ingredients the recipe calls for. So the deck isn't "some pairs" — it's derived from the recipe.

fun buildDeck(ingredients: List<Ingredients> = cakeIngredients, random: Random = Random.Default) =
    ingredients
        .flatMap { ingredient -> List(ingredient.requiredAmount * 2) { ingredient } }
        .shuffled(random)
        // Ids come after the shuffle so they stay unique across repeated symbols.
        .mapIndexed { index, ingredient -> MemoryCard(id = index, ingredient = ingredient) }

One pair per unit needed: 3 hearts becomes 6 heart cards, 20 cards and 10 pairs in total. Six heart cards are the same object, so numbering after the shuffle is what guarantees 20 distinct ids. Every lookup goes through that id.

The consequence is that symbols repeat and any two hearts match — a departure from classic memory, and the price of tying the board to the recipe. A conscious trade, not an oversight.

Injection without a framework

Both constructor parameters are defaulted, so Kotlin emits a no-arg constructor and viewModel() builds it without a factory — while a test can still pass Random(42) for a reproducible board. Hilt would add a Gradle plugin and annotation processing to solve what two default parameters already solve. Being able to say "I chose not to, and here's the mechanism instead" beats having used it reflexively.

The early resolve

The most player-focused code in the project

You miss a pair, a 1050ms timer starts, and you already know your next move. Most implementations swallow that tap and the game feels dead. This one cancels the timer, flips the missed pair down and reveals the new card — all in one state update, one frame.

if (state.isMismatched) {
    flipBackJob?.cancel()
    val settling = state.revealed.map { it.id }.toSet()
    _uiState.update { current ->
        current.copy(cards = current.cards.map { card ->
            when {
                card.id in settling -> card.copy(isFaceUp = false)
                card.id == cardId   -> card.copy(isFaceUp = true)
                else                -> card
            }
        })
    }
    return
}

The three-way when inside a single map is what makes it atomic. Two separate updates would produce a frame with three cards face-up.

Re-checking after the delay

flipBackJob = viewModelScope.launch {
    delay(CARD_FLIP_DURATION_MS + REVEAL_HOLD_MS)   // 350 + 700
    _uiState.update { current ->
        val stillWaiting = listOf(firstId, secondId).all { id ->
            current.cards.any { it.id == id && it.isFaceUp && !it.isMatched }
        }
        if (!stillWaiting) current else /* flip them down */
    }
}

A second is a long time. The player might tap a third card, or restart — in which case ids 3 and 7 now mean entirely different cards on a new board, and flipping them blindly would turn down cards the player just revealed. So the coroutine re-validates inside the same update that would change things.

Note the duration is flip time + reading time, not a magic 1050. CARD_FLIP_DURATION_MS is the same constant the animation uses, so changing the flip speed carries the wait along with it.

The general lesson

Any delayed operation must re-validate its assumptions when it wakes up. The world changed while it slept. cancel() covers the cases you thought of; the re-check covers the ones you didn't.

The flip

animateFloatAsState eases rotationY from 0° to 180°; the face swaps at 90°, hidden by the edge-on moment, which is what makes it read as one object turning rather than two images crossfading. cameraDistance pulls the vanishing point back so the turn isn't fish-eyed.

Two details worth the read. The front image carries its own rotationY = 180f to cancel the parent's half-turn — otherwise the art renders mirrored — and it must be a separate layer, since folding it into the parent would cancel the animation itself. And clickable sits outside the rotated layer, because hit testing happens in the layout's coordinate space and a rotating target would shrink to nothing at 90°.

An accessibility grace note: a face-down card announces "hidden card", not its symbol. Labelling it properly would let a screen reader read out the whole solution.

Why not LazyVerticalGrid

Because nothing is ever off-screen, which is the entire reason lazy layouts exist. All 20 cards must be visible at once — a memory game you have to scroll is one you cannot play. A weighted Column of Rows divides available space proportionally so the board fits any screen.

Self-check · 06
Why are card ids assigned after the shuffle?
Because the same Ingredients object appears on multiple cards — six heart cards are the same instance. Numbering after the shuffle guarantees 20 distinct ids regardless of duplication, and every lookup and flip-back operation goes through the id.
Why does isMismatched never become true for a matched pair?
Because revealed filters out matched cards, and both cards of a match are marked isMatched in the same update that turns the second one face-up. There's no intermediate state where two matched cards are face-up and unmatched — which is exactly what makes isMismatched derivable at all.
Name two situations that make the wake-up re-check necessary.
Early resolve — the player tapped a third card and the pair is already down, so these ids may now be legitimately face-up again. And restart — the deck was replaced, so ids 3 and 7 refer to different cards entirely.
07

Drag and drop

Compose's drag-and-drop sits on Android's platform drag-and-drop, which is why the payload is a ClipData holding a string rather than a Kotlin object — it's an API designed for cross-app transfer.

rememberUpdatedState

Two requirements in conflict

The DragAndDropTarget must be created once — recreating it every recomposition would re-register it with the platform mid-drag. But the callback it needs arrives as a method reference that is a new object every recomposition. Capture it directly inside the remember and you've frozen the first one forever.

val onDropped by rememberUpdatedState(onIngredientDropped)

val callback = remember {
    object : DragAndDropTarget {
        override fun onDrop(event: DragAndDropEvent): Boolean {
            // ...reads onDropped at call time, always current
        }
    }
}

rememberUpdatedState(x) returns a State that survives recomposition but whose .value is overwritten with the newest x each pass. The target captures the holder (stable) and reads .value at call time (current). One long-lived object, never a stale callback.

You'll want this again for any long-lived thing that captures a callback: LaunchedEffect(Unit), DisposableEffect, a remembered listener, a timer.

Modifier order is correctness

Modifier
    .dragAndDropTarget(...)     // 1st: registers the drop area
    .padding(vertical = 12.dp)  // 2nd: shrinks what's inside
    .scale(bowlScale)           // 3rd: visual only

Modifiers apply outside-in. Putting the target before the padding makes those 12dp part of the drop region — a near-miss still counts, a forgiving hit target for free. Putting scale last means the bowl visually swells 8% under a finger while its drop bounds stay still; scale it earlier and the target moves under the player's finger mid-drag.

Swap those three lines and the feature still "works", but becomes fiddly in a way that's very hard to diagnose.

A snapshot that goes stale

There's a dragAndDropSource overload that snapshots the composable into a graphics layer to use as the drag shadow. Convenient — until you notice the chip displays a live count. The snapshot is a recording, taken once, so after the first drag the shadow still shows "3" forever.

The fix is to draw the decoration by hand in drawDragDecoration: just the ingredient icon, centred in the chip-sized shadow canvas, at 0.9× the chip height so it stays visible under a fingertip. Nothing that can go stale.

Refusing a drag with null

transferData = { _ -> if (!canDrag) null else DragAndDropTransferData(...) }

No enabled flag, no separate disabled component — an empty chip simply declines to produce a payload and the platform never starts the drag. Better than a flag because there's no second source of truth to keep in sync: the source is unable rather than permitted not to. Paired with a 0.45 alpha dim, the player sees it and feels it.

Self-check · 07
What exactly does rememberUpdatedState fix here?
It bridges "this object must be created once" with "this callback changes every recomposition". Capturing the callback inside the remember block would freeze the first one — a stale closure. The State holder is stable while its value stays current.
Why is the payload a string id rather than the Ingredients object?
Because it crosses into platform drag-and-drop, which carries ClipData. Sending the object would require Parcelable and serialisation for no gain — the receiver already has the full ingredient list and can look up "heart" instantly. Send the key, not the object.
Where else in this codebase does the same "send the key" idea appear?
DialogText holding a @StringRes Int instead of a resolved String, and DialogSequenceId naming a conversation instead of passing the sequence around. Same instinct, three places.
08

Layout & art

Exactly one cat

A pattern worth naming

Originally each page drew its own cat, and the dialog drew one too. Opening a dialog gave you two — one dimmed by the scrim, one not, in slightly different positions. The fix wasn't to synchronise them. It was to make only one exist.

GamePageScaffold draws three children in order — page, overlay, cat — so the character sits above the scrim. Everything that wants to influence it reports a mood upward instead of drawing its own. When two components can disagree about something, make one of them the only one that exists; the bug becomes structurally impossible rather than carefully avoided.

The cat floats outside the page's layout flow, so pages need its size to keep that corner clear. That travels down through GamePageScope, and pages are declared as extension functions on it — the same idea as BoxScope.align(). It's a Dp and not a fraction on purpose: inside a weighted Row, fillMaxWidth(0.24f) would measure 24% of the leftover space.

The Scaffold trap

The app draws edge-to-edge so the pink background and the scrim reach the screen edges. Insets are then applied to content and the cat, but not to the root.

The comment in MainActivity records a real debugging session: setting contentWindowInsets = WindowInsets(0) on a Scaffold doesn't mean "don't consume insets" — it means "report zero insets to your content". Every page got an empty PaddingValues and the Mix button ended up under the navigation bar. Reading WindowInsets.safeDrawing.asPaddingValues() directly is unambiguous.

Pixel-art corners, drawn not stretched

The stepped corners of the dialog panel come from a custom Shape building a Path, not from the PNG they were designed as. Because the panel's height animates continuously between very different sizes, a stretched bitmap would distort the corner treads and thicken the border unevenly at every intermediate height. A path is computed from the actual size on every layout.

It's a data class so the background modifier's outline cache can compare instances — a regular class would use identity equality and blow the cache every frame.

The callout boxes on this page are drawn with that same two-tread staircase, reproduced as a CSS clip-path and layered as two nested fills — the same technique DialogFrame uses.

Knowing why an API is slow

DialogFrame uses two nested background fills rather than background + border. The reason is mechanical: for a generic (non-rounded-rect) outline, Modifier.border can't simply stroke the path — half the stroke would fall outside the bounds — so it strokes at double width into an offscreen layer and clears the middle with BlendMode.Clear. That's a saveLayer per draw-cache invalidation, and this panel resizes every frame for ~300ms on every dialog step. Two path fills allocate no layer at all.

Most people avoid APIs by superstition. Knowing the mechanism is a different thing, and it's a good answer to "have you done any performance work?"

Animated art

Compose's Image cannot animate GIFs — you get frame one, frozen. Coil can, with AnimatedImageDecoder registered in the Application class (it's ImageDecoder-based, so it needs API 28, which is the project's minSdk).

CharacterPlaceholder branches on LocalInspectionMode, falling back to a static Image inside Android Studio's preview renderer — which has no Coil loader, so without the branch every preview containing the cat would be empty. Generally useful: that's how you stub anything that can't work in a preview.

The finale's three Lottie animations all play below 1×. Stock Lottie files are authored as hero animations; as ambient decoration they're frantic. A two-second fix that transforms how the page feels.

Rejecting Material You

No dark theme, no dynamic colour. Material You derives a palette from the user's wallpaper — excellent for a productivity app, wrong for a pixel-art illustration where the pink page and cream panel are the artwork. The scheme maps every Material role explicitly, and the one that matters most is onSurface: it's what an unstyled Text inherits, and on a wallpaper-derived scheme it could land near-white, invisible on cream.

A defensible deviation from platform convention is a more interesting thing to discuss than compliance. The test is whether you can say why.

Self-check · 08
Why is the cat drawn by the scaffold instead of by each page?
Because there must be exactly one. When pages drew their own and the dialog drew another, opening a dialog produced two cats — one dimmed, one not. Drawing it once, declared last so it's above both page and scrim, makes disagreement structurally impossible.
Why a custom Shape instead of the PNG the art was drawn from?
Because the panel's height animates continuously. A stretched bitmap would distort the treads and thicken the border unevenly at every intermediate size; a path is recomputed from the real size on every layout. The art has no interior detail, so nothing is lost.
Defend disabling dynamic colour in two sentences.
The app is a fixed pixel-art illustration whose pink page and cream panel are the artwork, not a neutral surface — wallpaper-derived colours would repaint them differently on every device and break the composition. Material You exists to make utility apps feel personal; this isn't a utility app, and the constant palette is the product.

Testing

Three JUnit files, no emulator, no Robolectric. That isn't luck — it's the payoff for choices made much earlier.

DecisionWhy it makes tests possible
DialogText holds a @StringRes IntReading the catalog needs no Context
DialogStep holds no lambdas, no Compose typesThe script is comparable, printable, plain data
ViewModels import no ComposeGameViewModel() is constructible on the JVM

This is the real argument for the architecture. Not "MVVM is best practice" — "the game logic runs in milliseconds on the JVM because no part of it knows what a Context is."

Tests as specification

Read the test names of GameViewModelTest top to bottom and you have the game's rules:

the game opens on the mixing page with the intro running
the opening conversations chain intro to recipe to ran out, then start the hunt
clearing the board banks the ingredients and celebrates
a second hunt result is ignored while the celebration is still up
a page expression only shows through once the dialog is gone
an ingredient cannot be dropped more times than it was collected
an id that is not in the recipe is ignored
mixing unlocks only once the last unit is in the bowl

Backtick names are idiomatic for JVM unit tests. One caution: don't use them in androidTest — the Android runtime rejects spaces in method names on some API levels, and it fails at runtime rather than compile time.

The test class also builds itself a vocabulary with private extension functions — runToHunt(), runToMixing() — so GameViewModel().apply { runToMixing() } reads as "a game that has reached the mixing stage" and the test that follows can be about one thing. finishCurrentSequence() reads the step count from the sequence rather than hardcoding it, so adding a line of dialogue doesn't break the suite.

A regression test for a design decision

/**
 * The case that rules out `bowlCount == collectedIngredients`: on the opening screen
 * both are zero, and an empty bowl must not read as ready.
 */
@Test
fun `a fresh game is not ready to mix`() {
    assertEquals(false, GameUiState().isMixReady)
}

Without this, the "simpler" version of isMixReady looks appealing — and it's wrong, because before the hunt both values are zero and an empty bowl would report ready on the opening screen. A comment explains the trap; the test makes it permanent.

Talking points

The thirty-second pitch

It's an interactive birthday card built as a small game in Jetpack Compose — three screens, a memory-matching mini-game, and drag-and-drop mixing. The two things I'd point at are that the entire dialogue script is plain data rather than code, so adding a line is a one-line edit with no UI changes; and that all the game logic runs in JVM unit tests with no emulator, because nothing in it touches a Context.

Two claims, both specific, both verifiable by opening the repo. Better than "I built a game with Compose and MVVM".

The deliberate non-choices

Say these out loud in the README, each with its reason and the line at which it stops being right. Unjustified absence looks like ignorance; justified absence looks like judgement.

Not usedBecause
Navigation ComposeThree linear screens, no back stack — back is actively blocked — no deep links, no arguments to serialize.
HiltTwo defaulted constructor parameters give viewModel() a no-arg constructor and let tests inject a seeded Random.
Room / a repositoryA two-minute session with nothing to persist.
Material You / dark themeThe pink page and cream panel are the artwork; a wallpaper palette would repaint them per device.

Known gaps — say these before anyone finds them

Testing
MiniHuntViewModel has no testsThe most intricate logic in the codebase — early resolve, cancellable jobs, the wake-up re-check. Harder to test than GameViewModel because it schedules coroutines, so it needs kotlinx-coroutines-test and Dispatchers.setMain.
Accessibility
No end-to-end TalkBack passThere are genuinely thoughtful touches — face-down cards announce "hidden card" rather than their symbol, disabled buttons are marked disabled, the decorative cat is null-described. But drag-and-drop has no keyboard or switch-access alternative.
Maintainability
Two animations kept in sync by handThe dialog body's AnimatedContent and the footnote's Crossfade share timing constants but are separate animations. Extracting a shared AnimationSpec would make it structural rather than remembered.

Two gaps this page found and closed

Both were caught by writing the walkthrough, then fixed in the code. That sequence is the point worth making: documenting your own project is a review pass, and it turned up things the tests didn't.

Fixed
totalIngredients was hardcoded to 10It equalled cakeIngredients.sumOf { it.requiredAmount } only by arithmetic coincidence, so changing any requiredAmount would grow the deck while the constant stayed put — "11 / 10 pairs found" in the header, and Mix unlocking before the bowl was full. Three wrong behaviours, no compile error. Now derived.
Fixed
take(3) / takeLast(3) assumed exactly six ingredientsWith five, one item rendered in both rows; with seven, one disappeared. Both pages now use chunked(3) — the pattern the card grid was already using two functions away.

The honest version if it comes up: neither could actually fire with the current six ingredients. They were latent, not live. What makes them worth mentioning is the shape — a constant that duplicated a computable fact, and a slice that encoded a list length nobody had written down.

Before you post it

  • A GIF of the full playthrough at the top of the README. Non-negotiable for a game — nobody clones a repo to find out what it looks like.
  • A licence file. "Free for people to use" needs stating. MIT is the usual portfolio choice. Note it covers your code — if the art or the Lottie files have their own terms, say so separately and credit them.
  • CI running ./gradlew test. Low effort, and a README with a passing-tests badge is read very differently from one without.
  • Screenshots — most of them can come straight from the existing @Previews.

One honest note

This was built with AI assistance, and it's going up as a portfolio piece. Using AI tooling is normal and increasingly expected; what distinguishes people is whether they understand and can defend what shipped.
